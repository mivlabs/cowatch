# Recommendations Service

Content-based рекомендатель фильмов/сериалов для CoWatch: "что посмотреть
дальше", на основе каталога, загруженного из TMDB, и истории просмотров.

## История решения (важно для собеседования)

Первая версия этого сервиса пыталась угадать фильм по названию из
`rooms.current_movie_title`. Не сработало бы на реальных данных: пользователи
CoWatch делятся голыми ссылками (Rutube/YouTube/прямые файлы), а
`current_movie_title` фронтенд даже не отправляет — оно почти всегда пустое
(см. `frontend/src/pages/RoomPage.tsx`, запрос отправляет только `url`).
Vimeo, кстати, тоже упоминался в старом коде плеера, хотя из продукта уже
убран — отдельный мелкий техдолг, не относится к ML.

Решение: каталог теперь загружается ЗАРАНЕЕ из TMDB (`ml/import_catalog.py`),
а пользователь выбирает фильм ИЗ каталога при создании комнаты — тогда
привязка к контенту гарантированно чистая, без всякого угадывания. Это
изменение архитектуры в процессе работы — нормальная часть разработки, и
честный рассказ об этом на собеседовании звучит сильнее, чем "сразу всё
спроектировала идеально".

## Что это ЕСТЬ (MVP, честно)

- **TF-IDF + косинусная близость** по жанрам и описанию контента
  (`app/services/recommender.py`). Не нейросеть, не матричная факторизация —
  классический, объяснимый content-based baseline. Осознанный выбор: при
  малом числе пользователей и просмотров (см. `notebooks/eda_watch_patterns.ipynb`)
  collaborative filtering не соберёт достаточно сигнала, а content-based
  работает даже с одним просмотром на пользователя.
- **Cold-start fallback на popularity** — для новых пользователей без истории.
- **Каталог из TMDB** (`app/services/tmdb_client.py`, `ml/import_catalog.py`) —
  листаем готовые подборки "популярное" для movie и tv, идемпотентно
  сохраняем в `content_items` (upsert по `tmdb_id`). Никакого угадывания —
  каждая строка гарантированно настоящий фильм/сериал.
- **ETL просмотров временно сломан** (`app/services/etl.py`,
  `POST /admin/sync-watch-events`) — старая версия звала TMDB search по
  кривому названию, теперь это не нужно и не работает. Переделываем на
  следующем шаге, когда в `rooms` появится `content_id`, указывающий на
  каталог напрямую (пользователь выбирает фильм при создании комнаты —
  никакого matching по тексту не потребуется вообще).
- **Оценка качества** — leave-one-out по времени: прячем последний просмотр
  пользователя, смотрим, попадает ли он в top-K по остальной истории.
  Метрики: precision@k, recall@k, hit_rate@k.
- **MLflow** трекает эксперименты (`ml/train.py`) — параметры векторайзера,
  метрики, версия модели как артефакт.
- Пример прогона на демо-данных (`data/sample_*.csv`, 15 фильмов / 10
  пользователей / 31 просмотр): **precision@3 = 0.30, hit_rate@3 = 0.90**.
  Это метрики на **синтетическом** сэмпле, не на реальных пользователях
  CoWatch — см. `data/README.md`. Значения на реальных данных будут другими
  и появятся только после первого прогона ETL против прод-`rooms_db`.

## Чего это НЕТ (пока, roadmap)

Чтобы на собеседовании не рассказывать про то, чего нет в коде — по опыту
работы над остальными тремя репозиториями (см. корневой аудит техдолга),
явный список ограничений:

1. **Нет event streaming.** ETL читает чужую БД напрямую по HTTP-триггеру
   (`POST /admin/sync-watch-events`), а не по CDC/Kafka. На проде это
   работает только потому, что `rooms_db` маленькая. Правильное решение —
   Debezium/Kafka Connect на изменения `participants`, либо хотя бы Airflow
   DAG по расписанию вместо ручного триггера.
2. **Нет collaborative filtering / матричной факторизации** (implicit ALS,
   two-tower). Content-based — обоснованный выбор для MVP при текущем
   объёме данных, но это не "полноценная рекомендательная система" уровня
   Netflix — не называть так на собеседовании.
3. **Нет MLflow Model Registry с promotion-пайплайном.** `train.py` логирует
   в MLflow, но раздача в проде — простой файл `models/latest.joblib`,
   который `train.py` перезаписывает после каждого обучения. Ручной шаг,
   не автоматический canary/rollback.
4. **Нет мониторинга дрифта данных/качества модели в проде** (Evidently AI
   или аналог). `evaluate_leave_one_out` считается только офлайн, вручную,
   при запуске `train.py`.
5. **Нет ClickHouse для event-логов** (клики по рекомендациям, CTR). Пока
   логи только в `watch_events` (то, что посмотрели), не в том, что
   порекомендовали и на что кликнули — то есть нет online-метрик качества
   рекомендаций, только офлайн leave-one-out.
6. **`POST /admin/sync-watch-events` временно нерабочий** — см. "История
   решения" выше. Не вызывать до переделки на `room.content_id`.

## Запуск

```bash
# в докере — вместе с остальными сервисами CoWatch
docker compose up recommendations

# локально, для разработки ML-части (без Docker)
cd services/recommendations
pip install -r requirements.txt

# 1. загрузить каталог фильмов/сериалов из TMDB (нужен TMDB_API_KEY в .env)
python -m ml.import_catalog

# 2. обучить рекомендатель на демо-сэмпле (реальных watch_events пока мало, см. историю решения)
python -m ml.train --sample

# 3. поднять API
uvicorn app.main:app --reload
```
